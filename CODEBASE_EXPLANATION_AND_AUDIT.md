## 1. Executive Summary

This is an **npm-workspaces monorepo** (defined in `app/package.json`) building an Islamic lifestyle app named **Sakinah** (سكينة — "tranquility"). It contains:

| Piece | Tech | Purpose |
|---|---|---|
| `artifacts/mobile` | Expo ~57, React Native 0.86, React 19, expo-router | The user-facing app: Quran reader, adhkar counter, prayer times, Qibla, favorites, settings |
| `artifacts/api-server` | Express 5, Node ESM, pino logging, esbuild | REST API (`/api/*`) that proxies/caches external Islamic content APIs |
| `artifacts/mockup-sandbox` | Vite 7, React 19, Tailwind 4 | A dev-only "component preview server" (Replit-flavored scaffolding) |
| `lib/api-spec` | OpenAPI 3.1 YAML + Orval | **Single source of truth** for the API contract |
| `lib/api-zod` | Orval-generated Zod schemas | Runtime validation schemas derived from the spec |
| `lib/api-client-react` | Orval-generated TanStack Query hooks | Typed client the mobile app consumes |
| `lib/db` | Drizzle ORM + PostgreSQL | Database package — **currently a scaffold with an empty schema** |
| `scripts` | tsx | Placeholder hello-world script + a `post-merge.sh` hook |

**The defining idea:** the API is defined *contract-first*. You edit `lib/api-spec/openapi.yaml`, run Orval, and it regenerates both Zod validation schemas (`@workspace/api-zod`) and React Query hooks (`@workspace/api-client-react`). The mobile app never hand-writes fetch calls — it uses generated hooks like `useGetQuranSurahs()`.

The backend itself is a **read-only aggregation proxy**: it does not store content; it fetches from Quran Foundation (OAuth2 client-credentials), hadeethenc.com, hisnmuslim.com, and api.aladhan.com, normalizes the payloads, caches them in-memory with TTL + stampede protection, and serves a consistent JSON envelope.

## 4. The API Contract Pipeline

### 4.1 `lib/api-spec/openapi.yaml`

Defines 9 operations under server base path `/api`:

| Operation | Path | Notes |
|---|---|---|
| `healthCheck` | `GET /healthz` | `{ status: string }` |
| `getQuranSurahs` | `GET /quran/surahs` | 114 surah metadata |
| `getQuranReader` | `GET /quran/surahs/{surahId}` | surah + verses (Uthmani text, juz, page) |
| `getQuranAudio` | `GET /quran/surahs/{surahId}/audio` | recitation URL (Mishary Alafasy) |
| `getQuranTafsir` | `GET /quran/tafsir/{surahId}/{ayahNumber}` | Ibn Kathir (resource 169) |
| `getPrayerTimes` | `GET /prayer-times` | lat/long/date, Aladhan method=3 |
| `getHadiths` | `GET /hadiths` | paginated hadith list |
| `getAdhkar` | `GET /adhkar` | dhikr categories + items |
| `getDuas` | `GET /duas` | same shape as adhkar |

Common `502` response (`ApiError { message, source }`) is shared via components.

### 4.2 `lib/api-spec/orval.config.ts`

Runs **two** Orval outputs from the same YAML:

1. **`api-client-react`** → `client: "react-query"`, `mode: "split"`, with a **mutator** pointing at a hand-written `custom-fetch.ts` (so every generated hook goes through the custom fetch wrapper). `baseUrl: "/api"`.
2. **`zod`** → Zod schemas for params + responses, pinned to **Zod 3** (`version: 3`) because Orval ≥ 8.23 would otherwise emit Zod 4 syntax while the workspace installs zod 3.

A custom input transformer **forces the API title to `"Api"`** — a deliberate hack, because Orval derives output filenames from the title (`api.ts`), and the import paths in `index.ts` files assume that name. The YAML even carries a comment: *"Do not change the title, if the title changes, the import paths will be broken."*

Regenerate with: `npm run codegen --workspace @workspace/api-spec` (runs `orval` then a lib typecheck).

### 4.3 `lib/api-zod` (generated)

`src/generated/api.ts` exports Zod objects per operation, e.g.:

```ts
export const GetQuranReaderParams = zod.object({
  surahId: zod.coerce.number().int().min(1).max(114),
});
export const GetQuranReaderResponse = zod.object({ surah: ..., verses: ... });
```

All path/query params use `zod.coerce.*` (HTTP params arrive as strings). Only the server's `/healthz` route actually validates with these today (`HealthCheckResponse.parse(...)`).

### 4.4 `lib/api-client-react` (generated + hand-written glue)

- `src/generated/api.ts` — one React Query hook per operation (`useGetQuranSurahs`, `useGetQuranReader`, `useGetQuranAudio`, `useGetQuranTafsir`, `useGetPrayerTimes`, `useGetHadiths`, `useGetAdhkar`, `useGetDuas`) plus query-key factories (`getGetQuranReaderQueryKey`, …).
- `src/custom-fetch.ts` — the mutator. This is a thoughtfully written, runtime-agnostic fetch wrapper (~400 lines). Highlights:
  - `setBaseUrl(url)` — the mobile root layout calls it at startup; only relative `/api/...` paths get the prefix.
  - `setAuthTokenGetter(fn)` — optional bearer-token injection (unused by the app currently).
  - `ApiError` / `ResponseParseError` classes with rich error messages (parses `title`/`detail`/`message` from Problem-details-style bodies).
  - React-Native-safe body detection (comment explains RN's `response.body` is always `undefined`, so the code uses `=== null` checks deliberately).
  - BOM stripping, content-type sniffing, `responseType: "json" | "text" | "blob" | "auto"`, GET-with-body guard.

## 6. `artifacts/api-server` — Express Backend

### 6.1 Bootstrap

- **`src/index.ts`** — requires `PORT`, validates it numerically, `app.listen(port)` with pino logging.
- **`src/app.ts`** — middleware order: `pino-http` (with serializers that strip query strings and log only `id/method/url` + status) → `cors()` (fully open) → `express.json()` → `express.urlencoded` → mounts router at `/api`.
- **Build** — `build.mjs` bundles with **esbuild** to a single ESM `dist/index.mjs`, `esbuild-plugin-pino` for the pino-pretty transport, a CJS-compat banner (`createRequire`/`__dirname` shims), source maps, and a huge `external` list for native/unbundleable packages. Run with `node --enable-source-maps dist/index.mjs`.

### 6.2 Response contract (`src/lib/respond.ts`)

Every content endpoint returns one of two envelopes:

```jsonc
// success
{ "success": true, "data": <payload>, "meta": { ...optional } }
// error
{ "success": false, "error": { "code": "NOT_FOUND", "message": "المورد غير موجود" } }
```

Error user-facing messages are **in Arabic**; machine codes are English (`INVALID_SURAH_ID`, `UPSTREAM_UNAVAILABLE`, …). `handleApiError` maps:
- `NotFoundError` → 404 with its own code
- `UpstreamError` → 502/503 with generic Arabic message
- anything else → 500 `INTERNAL_ERROR`

Helpers: `isIntegerParam(value, min, max)` → `number | null`; `numberParam(value, fallback)`.

### 6.3 Error & network layer

- **`src/lib/errors.ts`** — `UpstreamError` (source, status 502/503) and `NotFoundError` (code, Arabic message).
- **`src/lib/network.ts`** — `fetchJson<T>(url, source, { timeoutMs = 15s })` using `AbortSignal.timeout`; non-2xx → `UpstreamError` (≥500 upstream → 503, else 502); response must be a JSON *object* (arrays rejected) else `UpstreamError`. Also `httpsUrl()` (upgrades `http:` → `https:` for audio links) and `intString()`.
- **`src/lib/cache.ts`** — the interesting bit: a **TTL cache with in-flight deduplication**. `cached(key, ttlMs, loader)` serves fresh entries immediately, joins an identical in-flight promise (prevents stampedes when a burst of clients misses the same key), and stores `{ value, expiresAt }`. No eviction policy — deliberately fine for a small fixed key space.
- **`src/lib/logger.ts`** — pino; redacts `authorization`/`cookie` headers; pretty transport only outside production.

### 6.4 Services

#### `quranService.ts` — Quran Foundation (QFC) integration

The most involved service. Details:

- **Environments** — `QFC_HOSTS` map for `prelive` and `production` (oauth + api hosts). `QURAN_ENV` (or `QF_ENV`) selects; `QURAN_OAUTH_URL`/`QURAN_API_URL` can override. A comment warns never to mix pre-live credentials with production hosts.
- **Auth** — OAuth2 **client-credentials** grant: `Basic base64(CLIENT_ID:CLIENT_SECRET)` + `grant_type=client_credentials&scope=content`. Token cached in a module-level `Map` with TTL = `expires_in − 60s` (min 5s). Missing credentials → `UpstreamError("Quran authentication", 503)`.
- **`getQuranJson(path)`** — sends `x-auth-token` + `x-client-id` headers; on **401 retries once** with a forced token refresh; 20s timeout; all failures funnel into `UpstreamError`.
- **Endpoints consumed** (content API v4):
  - `/chapters?language=ar` → mapped to `{ id, nameArabic, nameEnglish, revelationPlace, versesCount }`
  - `/verses/by_chapter/{id}?fields=text_uthmani,juz_number,page_number&per_page=300` → verses
  - `/chapter_recitations/7/{surahId}` → audio URL for reciter #7 (Mishary Alafasy)
  - `/tafsirs/169/by_ayah/{surah}:{ayah}` → Ibn Kathir tafsir
- **Caching TTLs** — chapters 12h, surah 12h, audio 12h, tafsir 24h. Keys like `quran:surah:${surahId}`.
- Defensive mapping everywhere: raw JSON fields go through `Number()`/`String()` with defaults, chapters filtered for `id > 0 && nameArabic`, sorted by id.

#### `hadithService.ts` — hadeethenc.com integration

- **Categories** — `categories/roots/` + `categories/list/` merged into a **two-level tree** (`HadithCategoryNode { id, titleAr, count, parentId, children }`), children sorted by Arabic title. Cached 24h. (Note: only two levels — deeper descendants are grouped but never attached, see audit.)
- **List** — `hadeeths/list/?category_id=…&page=…&per_page=…`, cached 1h per (category,page,perPage). `perPage` clamped to 1–50, page ≥ 1. Parses upstream `meta { current_page, per_page, total_items, last_page }` into `{ page, perPage, total, hasMore }`, with sane fallbacks.
- **Detail** — `hadeeths/one/?id=…` → `{ id, title, hadith, attribution?, grade?, explanation?, reference?, categories? }`. Optional fields included only when non-empty (spread-conditional pattern). Falls back to first category title when `reference` missing. 404 when id+title both empty.
- **Search** — `hadeeths/search/?phrase=…` with a **longer 25s timeout**; not cached (search queries are too varied — reasonable).

#### `adhkarService.ts` — hisnmuslim.com integration

- A **local manifest** `src/data/hisn-categories.json` (`HisnCategoryMeta { id, source, nameAr, count, order }`) defines categories; `source` is the numeric file id on the upstream CDN.
- `fetchHisnItems(source)` fetches `https://www.hisnmuslim.com/api/ar/{source}.json` with a spoofed `user-agent: Mozilla/5.0`, then takes **the first array-valued property** of the returned object (the upstream JSON shape varies per file — brittle but pragmatic).
- Items normalized to `{ id: "hisn-{source}-{ID}", categoryId, title, arabicText, translation?, source, repeatCount (≥1), order, audioUrl? (http→https) }`, cached 24h per category.
- `getAdhkarItem(id)` regex-parses the composite id back to source+item, re-fetches the category, and finds the item.

### 6.5 Routes

| Route | Handler | Validation |
|---|---|---|
| `GET /api/healthz` | direct | `HealthCheckResponse.parse` (only Zod use server-side) |

### 7.2 Root layout (`app/_layout.tsx`)

- Prevents splash-screen auto-hide; loads fonts; hides splash when ready (or on error).
- **API base URL resolution** (`resolveApiBaseUrl`):
  1. `EXPO_PUBLIC_DOMAIN` env (adds `https://` if missing)
  2. In dev: Expo `hostUri` + `EXPO_PUBLIC_API_PORT` (default 3000) → `http://{host}:{port}`
  3. Otherwise `null` + a dev warning.
  Result is passed to `setBaseUrl(...)` from the generated client.
- **RTL**: `I18nManager.allowRTL(true)` and `forceRTL(true)` on native — the whole app is Arabic-first; almost every `flexDirection` is `row-reverse` and text is `textAlign: 'right'`.

- Stack screens use `slide_from_left` animation (correct for RTL feel) and Arabic back title `رجوع`.

### 7.4 Error handling UX

- `components/ErrorBoundary.tsx` — class component (required for `componentDidCatch`), dev-only console logging, optional `onError` hook, resettable.
- `components/ErrorFallback.tsx` — full-screen Arabic fallback ("حدث خطأ غير متوقع") with restart via `reloadAppAsync()`; **dev-only modal** showing the stack trace in monospace.
- `components/RouteErrorBoundary.tsx` — adapts expo-router's `{error, retry}` to the fallback.
- Every screen with data uses the trio `LoadingState / ErrorState / EmptyState` from `components/ui.tsx`; `isOfflineError()` regex-sniffs error messages (`network|offline|fetch|…`) to switch the icon/message between "no connection" and "temporary problem", always with an Arabic retry button.

### 7.5 Design tokens & theming

- `constants/tokens.ts` — `spacing (6–40)`, `radii (12/18/26/999)`, `typography` scale (incl. `quranLarge: 27`, `quranMedium: 22` for scripture text), `motion` durations.
- `constants/colors.ts` — full semantic palette with **light + dark** sets ("warm paper, emerald, restrained gold" — background `#F7F4EC` / `#10241F`, primary `#176B55` / `#70B997`).
- `hooks/useColors.ts` — `useColorScheme()` picks the palette; components call `useColors()` everywhere. The palette *exists* for dark mode but no screen overrides the OS setting (settings toggle is unwired).

### 7.6 The component library (`components/ui.tsx`)

Single-file kit: `Screen` (safe-area padding, scroll or static), `AppHeader` (eyebrow + title + action), `IconButton`, `SectionTitle`, `QuickAction`, `PrayerCard`, `ReadingCard`, `DailyVerse`, `SearchBar`, `EmptyState`, `ErrorState`, `LoadingState`, plus `isOfflineError`. Everything is accessible (`accessibilityRole`/`Label`), testable (`testID`s like `surah-{id}`, `dhikr-counter`, `prayer-card`), and token-driven.

### 7.7 Build & serve scripts (Replit deployment flavor)

- **`scripts/build.js`** (~450 lines) — builds a **static Expo Go deployment**: finds a workspace root **by looking for `pnpm-workspace.yaml`**, starts Metro (`expo start --no-dev --minify --localhost`), health-checks `localhost:8081`, downloads iOS+Android bundles sequentially and manifests in parallel (10-min overall timeout), regex-extracts asset entries from the bundle JS, copies assets from disk, rewrites `httpServerLocation` URLs and manifest `launchAsset` URLs to `{baseUrl}{basePath}/{timestamp}/…`, and writes `static-build/{ios,android}/manifest.json`. Domain from `REPLIT_INTERNAL_APP_DOMAIN` / `REPLIT_DEV_DOMAIN` / `EXPO_PUBLIC_DOMAIN`.
- **`server/serve.js`** — zero-dependency Node HTTP server for `static-build/`: `GET /` or `/manifest` with an `expo-platform: ios|android` header → the platform manifest JSON; without it → an HTML landing page (template in `server/templates/`, with `exps://` deep-link for Expo Go); everything else → static files with a MIME map and a path-traversal guard (`path.normalize` + prefix check).

⚠ Both scripts assume **pnpm**/Replit infrastructure, while the repo root uses npm (see audit #F7).

## 11. Cross-Cutting Patterns

1. **Contract-first codegen** — one YAML → Zod + React-Query client. Drift between spec and server is the main maintenance hazard (see audit).
2. **Envelope discipline** — `ok()/fail()` helpers keep `{success, data, meta}` / `{success:false, error:{code,message}}` uniform.
3. **Defensive normalization** — upstream JSON is never trusted; every field goes through `Number()/String()/isJsonRecord()` with defaults and filters.
4. **TTL cache + stampede dedup** — `cached()` is the single caching primitive; keys are namespaced per provider.
5. **Error taxonomy** — `NotFoundError` / `UpstreamError` → mapped centrally in `handleApiError`; Arabic for humans, codes for machines.
6. **Raw-TS workspace packages** — `customConditions: ["workspace"]` + `exports: "./src/index.ts"` means libs are consumed as source; `tsc --build` project references provide typecheck ordering only.
7. **Accessibility & testability** — Arabic `accessibilityLabel`s throughout, `testID`s on key interactive elements (ready for Maestro/Detox-style flows, though no tests exist yet).
8. **RTL-first layout** — `forceRTL(true)` + pervasive `row-reverse` / `textAlign: 'right'`.

## 14. ✅ Audit — Strengths

1. **Clean monorepo separation.** Contract (`api-spec`) / validation (`api-zod`) / client (`api-client-react`) / server / app are cleanly isolated with workspace references; the dependency graph flows one way.
2. **Excellent hand-written fetch layer.** `custom-fetch.ts` handles RN quirks (missing `ReadableStream`, `URL` instanceof pitfalls), BOM, content-type sniffing, rich `ApiError` messages, and optional auth injection — production-grade.
3. **Robust caching design.** TTL + in-flight promise dedup in 40 lines, correctly sized TTLs per content type (static scripture 12–24h, lists 1h), namespaced keys.
4. **Disciplined upstream handling.** Timeouts everywhere via `AbortSignal.timeout`, retry-once-on-401 for OAuth, status-mapped `UpstreamError` (503 vs 502), defensive field mapping with sensible defaults.
5. **Consistent API envelope + centralized error mapping**, with user-facing Arabic and stable machine codes.
6. **Strong logging hygiene.** pino with header redaction (auth/cookies), request serializers that drop query strings (avoids leaking search phrases into logs), pretty dev transport only.
7. **Accessibility & testability baked in early** — Arabic a11y labels, roles, `testID`s on every interactive element.
8. **Sensible auth for QFC** — credentials never logged, token TTL derived from `expires_in` with a 60s refresh buffer, environment separation with an explicit warning comment.
9. **Thoughtful iOS 26 handling** — NativeTabs/liquid-glass with graceful fallback to classic themed tabs.
10. **Zero-dependency static server** with a path-traversal guard for serving built bundles.

## 15. 🚨 Audit — Findings & Risks

### 🔴 High — contract/implementation drift will break the app

**F1. The generated client does not match what the server actually returns (envelope mismatch).**
The OpenAPI schemas (and therefore the types mobile compiles against) describe **bare payloads** (`QuranReader { surah, verses }`, `PrayerTimes { date, …, timings }`), but `respond.ts`'s `ok()` wraps everything as `{ success: true, data: <payload> }`.
Consequences at runtime (untyped — `customFetch` never validates with the Zod schemas):
- `quran-reader.tsx` does `const { surah: surahData, verses } = readerQuery.data;` → both `undefined` → `surahData.nameArabic` **throws**.
- `prayer.tsx` reads `prayerQuery.data.timings` → `undefined` → screen always shows "لا توجد مواقيت متاحة لهذا اليوم".
- The surah list accidentally works only because the spec's top-level field is coincidentally also named `data`, so `data?.data` hits the envelope's `data`.
**Fix:** pick one — either add the `{success, data}` envelope to `openapi.yaml` and regenerate, or unwrap in `customFetch`. Ideally also validate responses with the generated Zod schemas at the boundary so drift is caught in CI.

**F2. `/api/adhkar` and `/api/duas` do not exist on the server.**
The spec (and the mobile `useGetAdhkar` / `useGetDuas` calls) define `GET /adhkar?categoryId=` and `GET /duas?categoryId=`, but the server only implements `/adhkar/categories`, `/adhkar/categories/:id`, `/adhkar/items`, `/adhkar/items/:id`. The Adhkar tab and counter therefore receive 404 `NOT_FOUND` ("المورد غير موجود"). Either add compatibility routes that reshape `adhkarService` output into the spec's `DhikrCollection` shape, or change the spec + app to the routes that exist.

**F3. Hadith list items don't match the spec.** Spec: `Hadith { id, title, text, source }` + `page/totalPages`. Server list: `{ id, title }` only + `{ page, perPage, total, hasMore }` meta. `more.tsx` renders `hadith.text` and `hadith.source` → blank "hadith of the day" card. (The detail endpoint `/hadiths/:id` — which *does* have text — isn't even in the spec.)

### 🟠 Medium — gaps & dead weight

**F4. The database layer is dead code.** `@workspace/db` is a declared dependency of the API server, `docker-compose.yml` provisions Postgres, `post-merge.sh` runs `db push`, but the schema is an empty template and no server code imports `db`. Decide: build the schema (favorites, reading positions — the UI already hints at both) or remove the package/compose file to reduce confusion.

**F5. Mobile "placeholder" screens are static.** `/qibla` (no magnetometer/location sensors — compass is decorative, needle rotation hardcoded at 38°), `/settings` (theme/text-size/reciter/notifications all unwired `Switch`es), `/favorites` (always empty). The quran-reader's tafsir card **always fetches ayah 1** regardless of which ayah is tapped (verse `Pressable`s have no `onPress` at all, despite the note promising "tap any ayah to save your place"), and audio opens externally via `Linking.openURL` rather than an in-app player.

**F6. No tests anywhere** (0 test files), no lint config (prettier installed but unused, no ESLint), no CI workflows. For a codebase with this much hand-rolled parsing/normalization logic, unit tests on the service `normalize*` functions would pay off immediately.

**F7. Package-manager identity crisis.** Root uses **npm** (`package-lock.json`, `npm run --workspaces`), but `post-merge.sh` and `mobile/scripts/build.js` assume **pnpm** (`pnpm --filter`, and `findWorkspaceRoot()` searches for `pnpm-workspace.yaml` — which does not exist, so `build.js` **throws immediately** outside Replit). Pick one manager (or make `findWorkspaceRoot` also accept `package.json` with `workspaces`).

**F8. Quran tafsir ayah validation is loose.** Route accepts ayah 1–286 (Al-Baqarah's count) for *any* surah; e.g. surah 110 has 3 ayahs, so `110/200` passes validation and surfaces an upstream error instead of a clean 400. Per-surah verse-count validation (available from `getChapters()`) would fix it.

### 🟡 Low — hygiene

- **F9.** `README.md` is **UTF-16 encoded** (renders as `i s l a m i c - l i b r a r y - s h a m e l a` with null bytes) and contains no setup docs — re-save as UTF-8 and document the run steps (§13 above).
- **F10.** `docker-compose.yml` hardcodes dev credentials (`library/library123`) and is listed in `.gitignore` yet present in the tree — clarify whether it should be tracked (a `.env.example`-style template would be better).
- **F11.** `respond.ts` and `network.ts` both define an identical `numberParam`; `quranService` re-implements token caching with its own `Map` instead of reusing `lib/cache.ts` (which also lacks a `get/set` API for primitives — adding one would unify it). `hadithService`'s category tree silently drops third-level descendants (`childrenByParent` only ever attaches to roots).
- **F12.** `adhkarService.fetchHisnItems` spoofs a browser `user-agent` and relies on "first array property" shape-sniffing — brittle against upstream changes; pin expectations with a test fixture.
- **F13.** `searchHadiths` and the QFC token fetch bypass `lib/network.ts`'s `fetchJson` (raw `fetch`) — inconsistent error mapping paths. Also `mockup-sandbox` pulls a very heavy devDependency set (Radix, framer-motion, recharts…) for an empty canvas — fine for dev, but worth isolating.
- **F14.** TypeScript version split: root pins `~5.9.3` while mobile uses `~6.0.3` — project references across that boundary can produce surprising type errors; align versions.
- **F15.** Wide-open `cors()` and no rate limiting are acceptable for a public read-only API, but the prayer proxy and search endpoint are unthrottled passthroughs to third parties — a small in-memory rate limiter would protect upstream goodwill.
- **F16.** `/+not-found.tsx` is in English while the entire app is Arabic — localize it.

## 16. Recommendations Roadmap

**Phase 1 — make the app actually work end-to-end (F1–F3)**
1. Add the `{success, data, meta?}` envelope to `openapi.yaml` responses (or unwrap in `customFetch`) → regenerate → fix `quran-reader`/`prayer` field access.
2. Add `GET /api/adhkar` + `GET /api/duas` routes that adapt `adhkarService` to the `DhikrCollection` shape.

6. Vitest unit tests for `normalize*
` mappers and `cache.ts`; contract test that runs every generated Zod schema against live server responses.
